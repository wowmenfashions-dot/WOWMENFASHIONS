# Shopping Cart Application

## 5-Stage Speckit Requirements Specification

**Project:** Shopping Cart / E-Commerce Application
**Starting Point:** Empty Blazor Server application with MudBlazor
**Development Method:** Speckit
**Architecture:** Modular Monolith
**Authentication:** Custom Authentication
**UI:** Blazor Server + MudBlazor
**Database:** Relational Database

---

# 1. Product Vision

Build a complete shopping cart and e-commerce application using the existing empty Blazor Server application.

The application shall support two types of users:

### Guest User

A visitor who has not authenticated.

A guest can:

* Browse products
* Search products
* Filter products
* View product details
* Add products to cart
* Modify cart
* Remove products
* View cart totals

Authentication is **not required** for shopping.

Authentication becomes mandatory only when the customer wants to proceed with purchasing.

### Authenticated Customer

A registered customer can:

* Manage their profile
* Manage addresses
* Maintain a shopping cart
* Checkout
* Place orders
* View order history
* View order details
* Manage wishlist
* Review purchased products

### Administrator

An administrator can:

* Manage products
* Manage categories
* Manage inventory
* Manage customers
* Manage orders
* Manage promotions
* View dashboard information

---

# 3. Five Development Stages

The application shall be implemented in five stages.

```text
Stage 1
Product Catalog
     ↓
Stage 2
Shopping Cart + Guest Cart
     ↓
Stage 3
Custom Authentication + Customer Account
     ↓
Stage 4
Checkout + Orders + Administration
     ↓
Stage 5

```

Each stage must:

* Compile successfully
* Run independently
* Preserve functionality from previous stages
* Include appropriate tests
* Avoid unnecessary future-stage implementation
* Follow the architecture established in the project

# STAGE 1 — PRODUCT CATALOG

## 1. Stage Objective

Create the product catalog and category functionality.

A visitor should be able to use the application without logging in.

At the end of this stage, the application shall function as a basic product browsing website.

---

# 1.1 Product Entity

The system shall maintain product information.

Required fields:

```text
Product
--------------------
Id
Name
Description
SKU
Price
DiscountPrice
CategoryId
ImageUrl
StockQuantity
IsActive
CreatedAt
UpdatedAt
```

Requirements:

* Product ID must be unique.
* SKU must be unique.
* Product name is required.
* Price must be greater than or equal to zero.
* Stock quantity cannot be negative.
* Inactive products must not be displayed to customers.
* Created and updated timestamps must be maintained.

---

# 1.2 Category Entity

The system shall support product categories.

```text
Category
--------------------
Id
Name
Description
ParentCategoryId
IsActive
CreatedAt
UpdatedAt
```

The design should support parent/child categories even if the initial UI only uses a single category level.

Example:

```text
Electronics
    ├── Computers
    ├── Mobile Phones
    └── Accessories

Clothing
    ├── Men
    ├── Women
    └── Kids
```

---

# 1.3 Product Listing

Create a product listing page.

Example route:

```text
/products
```

The page shall display:

* Product image

* Price
* Discount price
* Category

Products shall be displayed using MudBlazor components.

# 1.4 Product Search

# 1.5 Product Filtering

# 1.7 Pagination

# STAGE 2 — SHOPPING CART AND GUEST CART

## 2. Stage Objective

Implement shopping cart functionality.

Customers must be able to shop without creating an account.

---

# 2.1 Guest Shopping

Authentication must NOT be required for:

* Browsing
* Searching
* Filtering
* Viewing product details
* Adding products to cart
* Viewing cart
* Updating cart

---

# 2.2 Cart Entity

The system shall support carts.

```text
Cart
--------------------
Id
CustomerId
GuestCartId
CreatedAt
UpdatedAt
```

A cart can belong to:

* An authenticated customer
* A guest visitor

Only one active cart should exist for a customer.

---

# 2.3 Cart Item

```text
CartItem
--------------------
Id
CartId
ProductId
Quantity
UnitPrice
CreatedAt
UpdatedAt
```

---

# 2.4 Add To Cart

When a customer adds a product:

1. Verify product exists.
2. Verify product is active.
3. Verify quantity is valid.
4. Verify available inventory.
5. Check whether product already exists in cart.
6. Increase existing quantity or create a new cart item.

---

# 2.5 Guest Cart Identification

Guest carts shall be identified using a secure browser-side identifier such as a cookie.

Example:

```text
Browser
   ↓
GuestCartId
   ↓
Cart
   ↓
CartItems
```

The application must not rely on the browser to provide the product price.

---

# 2.6 Cart Page

Create:

```text
/cart
```

Display:

* Product image
* Product name
* Unit price
* Quantity
* Item total
* Cart subtotal
* Remove action
* Continue shopping
* Proceed to checkout

---

# 2.7 Cart Quantity

Customers shall be able to:

* Increase quantity
* Decrease quantity
* Enter quantity
* Remove item

Quantity must always be validated against inventory.

---

# 2.8 Cart Calculation

The server shall calculate:

```text
ItemTotal = UnitPrice × Quantity

Subtotal = Sum(ItemTotal)
```

Client-side totals shall never be considered authoritative.

---

# 2.9 Cart Price Validation

When displaying or modifying a cart, the server shall verify current product pricing.

The application must handle situations where:

* Product price changed
* Product became inactive
* Product is no longer available
* Inventory decreased

---

# 2.10 Cart Indicator

The main navigation shall display the cart count.

Example:

```text
Shopping Cart (3)
```

---

# 2.11 Guest Cart Persistence

A guest cart should survive:

* Page navigation
* Browser refresh
* Moving between product pages

The guest cart should have a configurable expiration period.

---

# 2.12 Guest Cart → Customer Cart

When a guest reaches checkout and authenticates:

```text
Guest Cart
    ↓
Login/Register
    ↓
Customer Account
    ↓
Merge Guest Cart
    ↓
Customer Cart
```

If an authenticated customer already has a cart, the application shall use a deterministic merge strategy.

Example:

```text
Guest:
Laptop × 1

Existing Customer Cart:
Laptop × 2

Result:
Laptop × 3
```

The final quantity must still respect inventory limits.

---

# 2.13 Checkout Authentication Requirement

When an unauthenticated user clicks:

```text
Proceed to Checkout
```

the system shall redirect the user to:

```text
Login / Register
```

The user cannot place an order without authentication.

---

# 2.14 Stage 2 Acceptance Criteria

Stage 2 is complete when:

* Guest users can add products to cart.
* Guest users can modify cart.
* Guest users can remove products.
* Guest users can view cart.
* Guest cart survives browser refresh.
* Cart totals are calculated server-side.
* Inventory is validated.
* Price changes are detected.
* Cart count appears in navigation.
* Checkout requires authentication.
* Guest cart can be merged into authenticated customer's cart.
* Existing Stage 1 functionality continues to work.

---

# STAGE 3 — CUSTOM AUTHENTICATION AND CUSTOMER ACCOUNT

## 3. Stage Objective

Implement custom customer authentication and account management.

The application shall NOT use ASP.NET Core Identity.

The application shall implement a dedicated authentication module.

---

Create:

```text
/register
```

Registration fields:

```text
First Name
Last Name
Email
Phone Number
Password
Confirm Password
```

Requirements:

* Email must be unique.
* Email must have valid format.
* Password must meet configurable security requirements.
* Password confirmation must match.
* Required fields must be validated.
* Password must never be stored as plain text.

---

# 3.2 Customer Entity


# 3.3 Password Storage

Passwords must be stored using a secure password hashing mechanism.

The application must never store:

```text
Password
PlainTextPassword
```

---

# 3.4 Login

Create:

```text
/login
```

User enters:

```text
Email
Password
```

The system shall:

1. Find the customer.
2. Verify account status.
3. Verify password.
4. Create authenticated session.
5. Record last login time.

---

# 3.5 Logout

Create logout functionality.

Logout shall invalidate the current authenticated session.

---

# 3.6 Authentication Session

Authentication shall use secure server-side authentication/session mechanisms.

Requirements include:

* Secure cookies
* HttpOnly
* Secure flag where applicable
* Configurable expiration
* Session invalidation
* Logout support

Authentication implementation must be isolated behind an authentication service.

---

# 3.7 Authorization

The application shall distinguish:

```text
Guest
Customer
Administrator
```

Customer-only functionality shall require authentication.

Admin functionality shall require administrator authorization.

# 3.8 Forgot Password

* Be securely generated

# 3.9 Email Verification

```text

                         │
          ┌──────────────┼──────────────┐
          │              │              │

          │              │              │
          └──────────────┼──────────────┘
                         │
                  Authentication
                      Session
                         │
          ┌──────────────┴──────────────┐
          │                             │
       Customer                       Admin
```

The rest of the application should depend on an abstraction rather than directly implementing authentication logic.

4. Database changes are implemented.

# 15. Important Design Constraints

The implementation must follow these constraints.

### Authentication

Custom authentication shall be used.

Do not use ASP.NET Core Identity.

### UI

Use MudBlazor components.

Do not introduce another UI framework.

### Guest Shopping

Do not require authentication for normal shopping.

Authentication is mandatory only when purchasing.

### Security

Never trust prices, totals, inventory or customer identity supplied by the browser.

### Business Logic

Do not place business rules directly inside Razor components.

### Database

Do not load entire tables when pagination/filtering can be performed by the database.

### Architecture

Avoid creating unnecessary microservices.

The initial application should remain a modular monolith.

### Extensibility

Payment, notification, inventory and other external integrations should use interfaces/abstractions.
